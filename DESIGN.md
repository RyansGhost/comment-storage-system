# rf-comments — design

A tiny, self-hosted comment service for `*.ryanfleck.ca`, served from
`https://comments.ryanfleck.ca`, written in Common Lisp.

This document is the plan that was drafted before implementation. It records
the requirements, the gaps in them, and the decisions taken to fill those gaps.

---

## 1. Requirements → decisions

| # | Requirement | Decision |
|---|-------------|----------|
| 1 | Collect/serve comments for many subdomains from `comments.ryanfleck.ca` | One service, multi-tenant by **site**. Each site has a short `key` (e.g. `blog`) and a list of allowed origins (e.g. `https://blog.ryanfleck.ca`). |
| 2 | Tiny admin GUI to enable sites and configure their style | Server-rendered `/admin` pages: sites (create/edit/enable/disable, origins, theme) and a moderation list (hide/show/delete). |
| 3 | Disqus-like install | A single `<script>` tag plus a `<div>`. `embed.js` injects an auto-resizing **iframe** pointing at `/thread`. |
| 4 | Email + display name to comment; comment hidden until email verified | New comments are `pending`. A verification link is emailed; clicking it publishes **that** comment, marks the email verified, and signs the user in. Signed-in users publish immediately. |
| 5 | AWS SES API for email | Direct call to the **SES v2 `SendEmail`** REST endpoint with a small in-house **SigV4** signer (ironclad + dexador). No AWS SDK dependency. |
| 6 | Users can log in to see their profile and comments | **Passwordless magic-link login** (sent through SES). `/me` shows the profile (editable display name) and every comment with its status, page link, and a delete button. |
| 7 | SQLite stores user, content, date, page | Tables `users`, `comments(site_id, user_id, page_url, page_title, body, created_at, status)`, `sites`, `tokens`, `sessions`, `schema_migrations`. |
| 8 | Dockerised, easy to deploy on a VPS/VPC beside other programs | Multi-stage Dockerfile → a single SBCL executable on `debian:trixie-slim`, run as non-root. `docker-compose.yml` binds `127.0.0.1:8080` so a shared reverse proxy (Caddy/nginx/Traefik) fronts it. |
| 9 | SQLite DB lives outside the container | The `/data` **directory** is a bind mount (`./data:/data`). It's a directory and not a file because WAL mode needs the `-wal`/`-shm` side files. |
| 10 | Easy to edit and test in Emacs | Plain ASDF project, SLY-first README (SLIME works too), `dev/start.lisp` bootstrap, FiveAM tests runnable from the REPL, `make test` for the shell. |

## 2. Gaps found and how they were filled

1. **Which domains may embed a site?** Each site stores allowed origins. The
   thread iframe responds with `Content-Security-Policy: frame-ancestors <origins>`,
   and the `page` URL a comment is posted against must belong to one of those
   origins. Disabled or unknown sites render an inert "comments unavailable" box.
2. **What identifies a "page"?** It's the canonical URL: scheme + host + path,
   with the query string and fragment dropped and a trailing `index.html`
   removed. `embed.js` sends `location.href` by default. A page can override
   this with `data-page-url="…"` (like `disqus_url`) when the same article
   lives at several URLs.
3. **Cookies inside an iframe.** Browsers increasingly block third-party
   cookies. Every embedding page is a `*.ryanfleck.ca` subdomain, so the iframe
   is *same-site* (cross-origin only), and `SameSite=Lax` first-party cookies
   keep working. If an admin adds a foreign domain, login inside the iframe may
   not stick there, but commenting via email verification still works.
4. **Spoofing a verified email.** Anyone can type anyone's email. So
   verification is **per comment**: a pending comment is published only by the
   link mailed for it. Without a session, being "verified" earlier doesn't
   auto-publish new comments.
5. **Spam/abuse with minimal security.** The service uses a hidden honeypot
   field, an in-memory per-IP rate limit on posting, a per-email limit on
   outbound mails (default 5 per hour), a maximum body length (5000 chars), and
   admin moderation (hide/delete).
6. **CSRF and XSS.** All HTML is generated by Spinneret, which escapes by
   default. Comment bodies are plain text, with blank lines → paragraphs and
   newlines → `<br>`. Every state-changing `POST` must carry an `Origin` (or
   `Referer`) matching `PUBLIC_URL`, as OWASP's origin-verification defence
   recommends. Cookies are `HttpOnly; Secure; SameSite=Lax` (`Strict` for
   admin).
7. **Admin authentication.** A single admin whose password comes from the
   `ADMIN_PASSWORD` env var. A login form creates a DB-backed admin session.
   Comparison is constant-time, and an unset password disables `/admin`.
8. **Token storage.** Email-link tokens and session ids are 256-bit random
   values. Only their SHA-256 hash is stored, so a leaked DB dump can't be
   replayed. Email tokens expire after 48 h and are single-use. Sessions last
   90 days (admin: 12 h).
9. **Dates.** All dates are stored as UTC ISO-8601 text (`2026-11-06T15:41:00Z`).
   It's readable in `sqlite3` and sorts correctly as text.
10. **Schema evolution.** Numbered migrations live in Lisp and are applied at
    startup inside a transaction. `schema_migrations` records which have run.
11. **Concurrency.** Hunchentoot uses a thread per connection. A single SQLite
    connection is guarded by a lock, with `journal_mode=WAL`,
    `busy_timeout=5000`, and `foreign_keys=ON`. That's ample for a personal
    comment box.
12. **Email in development.** `EMAIL_BACKEND=log` prints the email, including
    the link, to stdout instead of calling SES. Tests use a capture backend.
13. **Behind a reverse proxy.** `TRUST_PROXY=true` makes the rate limiter use
    `X-Forwarded-For`. The proxy terminates TLS.
14. **Backups.** `sqlite3 data/comments.db ".backup backup.db"` works against
    the live DB from the host. This is documented in the README.
15. **Styling.** Each site has a theme: accent colour, text colour, background,
    border colour, font stack, corner radius, and a free-form "custom CSS"
    textarea. These are emitted as CSS custom properties inside the iframe. The
    default background is `transparent`, so the widget blends into the host
    page.
16. **Replies/threading, markdown, avatars, notifications.** These are out of
    scope for "tiny". The schema leaves room (`parent_id` can be added by
    migration).

## 3. Architecture

```
 blog.ryanfleck.ca page
 ┌───────────────────────────────────────────────┐
 │ <div id="rf-comments"></div>                  │
 │ <script src=".../embed.js" data-site="blog">  │──┐ injects
 │ ┌───────────────── iframe ──────────────────┐ │  │
 │ │ comments.ryanfleck.ca/thread?site&page    │◀┼──┘
 │ │  list + form (server-rendered HTML)       │ │  postMessage(height)
 │ └───────────────────────────────────────────┘ │
 └───────────────────────────────────────────────┘
                         │ HTTPS (Caddy/nginx on the VPS)
                         ▼
 ┌──────────────── docker: rf-comments ───────────────┐
 │ SBCL executable · Hunchentoot + easy-routes        │
 │  web.lisp   – /thread, /comment, /verify, /login,  │
 │               /me, /embed.js, /healthz             │
 │  admin.lisp – /admin/*                             │
 │  email.lisp – SES v2 + SigV4 (or log backend)      │──▶ email.<region>.amazonaws.com
 │  db.lisp    – cl-sqlite, migrations                │
 └───────────────────────┬────────────────────────────┘
                         │ bind mount
                    ./data/comments.db  (host)
```

### Libraries (Quicklisp dist 2026-01-01)

| Concern | Library | Why |
|---|---|---|
| HTTP server | hunchentoot + easy-routes | The most battle-tested CL server. easy-routes adds declarative routes. |
| SQLite | sqlite (cl-sqlite) | Thin, parameterised-query binding over libsqlite3. |
| HTML | spinneret | S-expression HTML with escaping by default. |
| JSON | com.inuoe.jzon | Fast, strict, and well maintained. |
| Crypto | ironclad | SHA-256, HMAC (SigV4), and secure random. |
| HTTP client | dexador | For SES calls. |
| Misc | cl-ppcre, quri, bordeaux-threads | Regexes, URL parsing, locks. |
| Tests | fiveam | The de facto test framework, with REPL-friendly `run!`. |

### Routes

| Method | Path | Purpose |
|---|---|---|
| GET | `/embed.js` | Loader script |
| GET | `/thread?site=&page=&title=` | iframe document: comments + form |
| POST | `/thread/comment` | Submit a comment |
| GET | `/verify?token=` | Verify a comment, sign in, then redirect to the page |
| GET/POST | `/login` | Request a magic link |
| GET | `/login/callback?token=` | Consume the magic link |
| GET | `/me` | Profile and own comments |
| POST | `/me/name`, `/me/comments/:id/delete`, `/logout` | Profile actions |
| GET | `/api/comments?site=&page=` | Read-only JSON (for static-site builds and integrations) |
| GET | `/healthz` | Liveness probe |
| GET/POST | `/admin/login`, `/admin/logout` | Admin session |
| GET | `/admin` | Sites list and recent comments |
| GET/POST | `/admin/sites/new`, `/admin/sites/:id` | Create/edit a site, including its theme |
| POST | `/admin/comments/:id/{hide,publish,delete}` | Moderation |

### Data model

```sql
sites      (id, key UNIQUE, name, origins TEXT /* newline separated */,
            enabled INT, theme TEXT /* JSON */, created_at)
users      (id, email UNIQUE /* lowercased */, display_name, verified_at, created_at)
comments   (id, site_id→sites, user_id→users, page_url, page_title, body,
            status /* pending|published|hidden */, created_at, published_at,
            ip_hash)
tokens     (id, token_hash UNIQUE, user_id, comment_id NULL, purpose
            /* verify|login */, expires_at, used_at, created_at)
sessions   (token_hash PK, user_id NULL, kind /* user|admin */, created_at, expires_at)
schema_migrations (version PK, applied_at)
```

## 5. Implementation plan

1. ASDF systems `rf-comments` and `rf-comments/tests`, with a source file per concern.
2. `util` (time, tokens, hashing, URL canonicalisation, validation) → `db`
   (connection, migrations, queries) → `email` (SigV4, SES, log backend) →
   `views` (layout, CSS, themes) → `web` and `admin` (routes) → `main` (start,
   stop, executable entry point).
3. Static `embed.js` with iframe injection and a postMessage resize listener
   that checks the message origin.
4. FiveAM tests: unit (URL canonicalisation, SigV4 against AWS's published
   vectors, tokens, rendering) plus integration (start the server on a random
   port with a temp DB and the capture email backend, then drive the full
   post → verify → publish → login → profile → admin flows with dexador).
5. Dockerfile (build → runtime), `docker-compose.yml`, `.env.example`, `Makefile`.
6. README with install, embed snippet, deployment (Caddy/nginx), SES setup
   (domain verification, sandbox, IAM policy), backups, and Emacs setup (SLY,
   Quicklisp, paredit, corfu, workflow).

## 6. Enhancements after reading *Lisp for the Web*

Each enhancement shipped on its own branch.

### Route macros (book ch. 2: macros against duplication)

`src/routes.lisp` defines `defpage` (HTML GET plus default security headers)
and `defaction` (POST). `defaction` always runs `@same-origin`, then
`@no-cache`, then any route-specific decorators, so CSRF protection is part
of the route's definition, not something each handler must remember. A test
checks easy-routes' registry so that no POST route can skip it.
`with-valid-inputs` flattens validation chains.

### Comment observers (book ch. 4: CLOS method combinations)

`src/events.lisp` turns `publish-comment`, `hide-comment` and
`remove-comment` into generic functions of `(comment by)`, where `by` is
`:author` or `:admin`. Primary methods only change the database. Side
effects are `:after` methods:

- `(comment by)`: write `moderation_log` (migration 2), shown as "Activity"
  in the admin.
- `(comment (by (eql :author)))`: email `ADMIN_EMAIL` about the new comment.
  It's specialised on the actor, so admin moderation never notifies.

The generic functions use a custom `observed` method combination: standard
semantics, except each `:after` method runs in its own error handler. A
broken observer, even one added later from a REPL, is logged and can't fail
the request. Signed-in posts are created `pending` and immediately
published through `publish-comment`, so every publish takes one code path.

### Stable thread ids (book ch. 4: "On natural IDs")

A page URL is a natural key, and natural keys change: slugs get renamed and
domains move. Migration 3 adds `threads(site_id, page_key, url, title)`,
with `page_key` unique per site, and `comments.thread_id`. Each existing
`(site_id, page_url)` pair is backfilled as a URL-keyed thread.
`comments.page_url` stays the URL the comment was posted from
(requirement 7).

- The key is the embed's `data-page-id` when present, else the canonical
  URL. A page id equal to an old URL adopts that URL's thread.
- GET `/thread` never creates rows. POST creates the thread on first
  comment. A page-id thread updates its stored URL/title whenever its page
  is viewed elsewhere.
- Links in emails, profiles and the admin use the thread's current URL.
- Admin `POST /admin/threads/:id/move` re-keys or re-points a thread, merging
  into an existing thread with the same key.

### Counts and stats (book ch. 5: push aggregation to the database)

The book runs MapReduce inside MongoDB rather than fetching every document.
Here the same idea is a single SQL `GROUP BY` per question (see
"Aggregates" in `src/db.lisp`):

- `GET /api/counts`: published counts for up to 100 thread keys (page
  URLs, canonicalised and checked against the site's origins, or page ids).
  Keys come back exactly as sent; unknown or foreign keys get 0. It has CORS
  for the site's origins and `Cache-Control: max-age=60`. `static/count.js`
  batches every `[data-rf-count]` element on a page into one request.
- Admin stats: status counts per site, comments per day for 30 days (CSS
  bars, CSP-safe), and the top 10 threads.

### Opt-in live REPL (the book's live-system development, in production)

`src/repl.lisp` starts Slynk only when `SLYNK_PORT` is set.

- Slynk and the contribs SLY requests are compiled into the executable by
  `build.lisp`. They aren't dependencies of the main system, which never
  reads `slynk:` symbols.
- **Authentication:** Slynk compares each connection's first packet with
  `~/.sly-secret`. The service requires `SLYNK_SECRET` (16+ characters),
  writes it to a private `HOME` under `/tmp` (mode 700/600), and checks
  Slynk reads it back; otherwise no REPL starts (fail closed).
- **Binding:** `SLYNK_INTERFACE` defaults to `127.0.0.1`.
  `docker-compose.repl.yml` binds `0.0.0.0` inside the container and
  publishes to `127.0.0.1:4005` on the host, so access is via SSH tunnel.
- **Hardening:** out of the box, a client with the wrong secret makes
  Slynk's accept thread signal an unhandled error. That kills a
  non-interactive Lisp, which would be a denial of service by anyone who can
  reach the port, and it leaks the socket. `harden-slynk` wraps
  `authenticate-client` (close the socket) and `accept-connections` (log and
  keep serving).
- **CI checks:** the default container has no listener on 4005; an opt-in
  container survives a wrong secret and completes a real protocol handshake
  with the right one.

### Gravatar profile images

Comments show Gravatar images, looked up by SHA-256 of the trimmed,
lowercased email (Gravatar's current scheme;
`https://gravatar.com/avatar/<hash>?s=80&d=<default>&r=g`).

- **Privacy:** pages never contain that hash or a gravatar.com URL. It
  would reveal emails to anyone guessing addresses, contradicting "Email
  (never shown)", and would send every reader's IP to Gravatar. Instead,
  migration 4 gives each user a random `avatar_key`, pages use
  `/avatar/<key>`, and the server fetches and serves the image from our own
  origin, so CSP `img-src 'self'` is unchanged.
- **Caching:** in memory for 24 h (at most 2000 entries); responses carry
  `Cache-Control: max-age=86400`.
- **Safety:** only PNG/JPEG/GIF/WebP are accepted from upstream. An SVG
  served from our origin could carry script, so the avatar responses also
  send `Content-Security-Policy: default-src 'none'`.
- **Failure handling:** a stale cached copy, else a generated SVG initial
  (cached 5 minutes).
- **Attribution:** "Profile images are provided by Gravatar." appears at
  the bottom of the comment section, under the form, where readers look for
  service notes. The profile page explains how to change your image.
  `AVATARS=off` removes images, note and route.
